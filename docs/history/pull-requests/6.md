## Description

## What this lets the user do

- Get a specification draft that knows the project's ignore rules and check commands.
- See, before approval, each project rule that limited the request, each open question and each need that the draft omits.
- See which files the Scout will read, before a run exists.
- Repeat `authorize-pilot` safely, and get the next command from `status` and from failed commands.

## Why

Run `trial-02` (pilot project, 16 November) stopped at a draft that could not be approved. Run records show:

- The Scout context had 4 files, 10,791 bytes: `AGENTS.md`, `README.md` and two task paths. It had no `.gitignore` and no check commands.
- The draft put committed samples in an ignored path, and planned a deliverable that `node --test` cannot check.
- A stale rule in the project `AGENTS.md` removed all code from the plan. Nothing reported this.
- A second `authorize-pilot` asked for the typed confirmation, then failed with a raw `EEXIST`.
- `status` gave no next step. `resume` without `--run` gave a generic recovery line.

## Changes

| Area | Change |
| --- | --- |
| Scout context | The committed root `.gitignore` is required context. The prompt states the check and verifier commands from `aegean.json`. |
| Draft format | New required fields: `verification`, `coverage`, `constraints`, `openQuestions`. Aegean writes them to `review-notes.md` in the specification folder. A draft without them, or without Requirement and Scenario headings, pauses the run. |
| `project check` | New `agentContext` field: the files that the Scout will read, with sizes. A missing or oversized required file fails here. No model call, no run. |
| `authorize-pilot` | A repeat with the same limits reports the saved authorisation with no prompt. Different limits or an expired authorisation fail with a clear message. The file is never replaced. |
| Guidance | `status`, the draft stop and failed commands give `next` or a specific `recovery` line. Guidance grants no permission. |
| Policy | `toolchain.json` policy is `0.5.0`. MODEL-USAGE requires a version change when context selection changes. |

Workflow rules stay pure: `src/domain/scout.ts` and `src/domain/next-steps.ts` have no I/O.

## Review points

1. **Policy 0.5.0 has a cost.** Each enrolled project must set `standardVersion` to `0.5.0`. A run made with 0.4.0 cannot resume; `status` and `cancel` still work. Host qualification is necessary again after installation.
2. **One existing assertion changed.** The pilot test expected a repeated identical request to fail. It now expects a report of the saved decision, no human prompt and an unchanged `pilot.json`. A request with different limits must still fail. The "no replacement, no reset" intent has stronger evidence than before.
3. **One test used `0.5.0` as its example of a changed policy version.** It now uses `99.0.0`.
4. **The stricter draft format can pause a run after one charged Scout call.** The rate is unmeasured. The previous run used 17,605 tokens for that call.
5. **A project rule still limits the Scout.** The Scout obeys the rule and reports it. It does not override the rule.
