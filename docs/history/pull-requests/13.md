## What this changes

Three checks for the build stage, before the first real run reaches the Builder. All three move a judgement from an agent to code, or route a fault to the party that can correct it.

1. **Base commit check.** Before the first build, the verifier runs the protected tests once on the unchanged base commit (public checks do not run there). The verifier receipt now records a pass or fail result for each protected test case.
   - If every test passes on the base commit, the run stops (`escalated`) before any Builder call: those tests cannot show that the change works.
   - Otherwise `baseline.json` in the run folder records the result for each requirement. `aegean status`, the local `aegean publish` summary and `publication-review.md` name the requirements whose tests already passed before the change.
   - An inconclusive check pauses the run. Resume repeats the check without another Auditor call.
2. **Allowed paths.** The Scout writes `allowed-paths.txt` in the specification. The human approves it with the rest of the specification and can edit it first.
   - Verification compares the changed paths with the file before the protected tests run. A change to another path fails verification, and the Builder gets a repair that names the paths.
   - A draft or a human edit with an invalid file cannot be recorded. Local approval and contract revision refuse a missing or invalid file.
   - `aegean guide` offers `allowed-paths.txt` with the other specification files at review.
   - `aegean revise --scope implementation` refuses a human edit outside the list. A scope problem in your own edit comes back to you, never to a Builder repair. To widen the list, edit it and use `--scope contract`.
3. **Finding owners.** The independent reviewer gives each finding the owner `builder`, `spec` or `factory`.
   - Only `builder` findings reach the Builder. A `spec` or `factory` finding stops the run and uses no repair.
   - The reviewer now gets the same public verification feedback as the Builder (failure reason and failed requirement identifiers), and the prompt tells it that `spec` and `factory` stop the run.

Also: the `ARCHITECTURE.md` and `OPERATIONS.md` sentence that said the Builder never gets "arbitrary Auditor prose" was wrong: the Builder has always received the review findings. Both now say what it gets and what it does not.

## Decisions you can reverse

- A suite that passes completely on the base commit stops the run. A suite that passes in part only shows a flag.
- A specification fault ends the run. A contract correction in the same run would need a new run state. The control ledger schema is strict and keeps finished runs, so a new state would stop an older release from reading the ledger after a rollback. This PR changes no ledger schema.
- A scope breach by the Builder uses one Builder repair (it is a failed verification), not a pause.
- A human implementation revision outside the list is refused, not checked in verification. The first full-suite run found this: without it, a human edit outside the list became a Builder repair that would undo the edit.
